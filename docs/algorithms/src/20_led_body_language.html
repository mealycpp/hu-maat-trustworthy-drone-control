1. Purpose and context

For visitors, the state of each simulated aircraft is shown on two LED visuals per model (front LED and ID strip). The colour is a function of telemetry and chat activity. The design constraint is load: each colour change is a Gazebo visual_config service call, and too many calls make odometry go stale, after which the supervisor refuses moves (Algorithm 9). The program therefore repaints only on change, under a global request budget, and prioritises urgent colours when the budget is short. It never commands an aircraft.

2. Inputs, outputs

  • Inputs: GET :8765/api/state every 0.25 s; GET :8766/api/ops/chat/history every 1 s (new message ids; first poll only primes).
  • Output: /world/<world>/visual_config requests (ambient, diffuse, emissive set to the colour), 0.5 s timeout each; on SIGTERM/SIGINT all LEDs are restored to white.

3. Algorithm

Algorithm 20.1 DECIDE (pure colour rule)
Source: acceptance/light_show.py: decide, motion_class, nearest_teammate
1function DECIDE(d, fleet, now, flags)
2 if d.mode = FAULT or d.fault or d.telemetry = false then return (fault, RED blinking 1 Hz)
3 if nearest teammate distance (3D, any mode) < 1.0 m then return (tight, RED)
4 if now < flags.talk_until then return (talking, BLUE) // 0.6 s after a new chat line
5 if goal_t0 ≤ now < goal_t0 + 1.5 s and now − goal_t0 ≥ index·0.25 s then
6 return (goal, hue = index/n) // rainbow chase across the fleet
7 if d.mode = QUEUED then return (queued, AMBER blinking, period 2.4 s)
8 if d.mode ∈ {TAKEOFF, LANDING} then return (transit, CYAN)
9 if d.mode ∈ {MOVE, TURN, SPIN, FORMATION} and (error unknown or ‖p − target‖ > 0.12) then return (moving, AMBER)
10 if d.mode ∈ {HOVER, MOVE, TURN, SPIN, FORMATION} then return (set, GREEN)
11 return (parked, DIM WHITE) // READY/GROUNDED/WAITING/unknown
Algorithm 20.2 GoalDetector and repaint loop
Source: acceptance/light_show.py: GoalDetector.update, TokenBucket, chat_speakers, run_body
11function GOAL-UPDATE(fleet) // once per new state sample
12 A ← airborne aircraft with class moving/set; W ← (W ∪ {moving in A}) ∩ A
13 if any aircraft in TAKEOFF/LANDING/QUEUED or |A| < 2 then return false
14 if all of A are set then fired ← |W| ≥ 2; W ← ∅; return fired
15 return false
16every 0.1 s do
17 if new state sample and GOAL-UPDATE(fleet) then goal_t0 ← now
18 wanted ← [ (priority, name, rgb) for aircraft whose DECIDE colour ≠ last painted colour ]
19 priority: fault, tight 0; talking 1; goal 2; others 3
20 for (·, name, rgb) in sorted(wanted) do
21 if not bucket.try_take(2) then break // 2 parts per aircraft
22 if PAINT(name, rgb) succeeded then last[name] ← rgb // cache only on success
23TokenBucket: tokens ← min(burst, tokens + Δt·rate); take if tokens ≥ n (rate = burst = max_rps)

5. Complexity

O(N²) per tick for nearest-teammate distances (N = 5); repaint work bounded by the token bucket.

6. Properties

Guaranteed

  • Read-only with respect to flight: only GET requests to the supervisor and chat, and visual service calls.
  • Average visual-service request rate ≤ max-rps (token bucket), and no request for an unchanged colour; failed paints are retried later rather than cached.
  • Fault and proximity colours pre-empt every other rule and are painted first when the budget is short.
  • The goal effect fires at most once per transition from "≥ 2 moving" to "all set", never while any aircraft is taking off, landing or queued, and not for a single-aircraft move.
  • decide is a pure function (testable without Gazebo).

Not guaranteed

  • The "tight" rule uses 3D distance to any teammate including parked ones and is a display rule (1.0 m), not the supervisor watchdog (0.82 m).
  • Blink rules change colour every half period, consuming budget continuously while active.
  • Colours lag the state by up to one poll plus budget delay.
  • If the state poll fails, the poller keeps the last sample, so colours continue to be computed from stale data (blink rules keep running); there is no "unknown / no data" colour.
  • The goal rule precedes the mode rules, so during the 1.5 s chase parked drones also show the rainbow; the hue index is the drone's position in the fixed name list (n = 5), not among the airborne ones.
  • Only an explicit telemetry: false selects the fault colour; a missing field does not.
  • A paint updates two visuals with separate requests; if one of them fails the drone can show mixed colours until the retry succeeds.
  • Restoring white at exit sends 10 requests outside the token bucket. The optional --mode party effect (random rainbow/strobe, budgeted with blocking take) is not covered by this specification.
  • Colour coding is the only channel: red (fault and tight) and green (set) are hard to separate for viewers with red–green colour-vision deficiency; fault is distinguished from tight only by blinking.
  • The effect on odometry freshness is argued, not measured here; the program logs request rates every 10 s, but no recorded log was evaluated.

8. Comparison with alternatives and related work

Using lights to make a robot's internal state legible to bystanders is an established topic in human–robot interaction, and flight controllers have their own LED conventions. The table compares the implemented colour language with these.

ApproachIdeaEvidenceRelation to ours
Expressive lights for state revealing, Baraka & Veloso [1]Formal mapping from robot state to parameterised light animations (colour, pattern, speed) on a mobile service robotUser studies on the CoBot robots: designed lights improved understanding of robot state and actionsSame goal (state legibility). Ours maps a small state set to colours by a fixed priority rule; patterns are limited to on/off blinking; no user study.
Communicating directionality in flying robots, Szafir, Mutlu & Fong [2]Signal designs (including light-based ones) that show a flyer's intended directionUser study: several designs improved viewers' prediction speed and accuracy over no signallingOurs shows status (moving / set / fault), not intended direction; the observer cannot tell where a drone will go.
Flight-controller status LEDs, PX4 [3]Standard RGB UI-LED codes for arming, GPS lock, low battery, failsafe and errorsDe facto convention known to pilotsOur colours conflict with it: amber means "moving" here but "low battery" in PX4; green means "set in slot" here but "armed with GPS lock" there. Acceptable in a simulator for visitors, misleading if carried to real aircraft.

Honest assessment. The engineering contribution is load control: change-only repaint, a shared token bucket and priority ordering keep the visual service calls bounded so the simulator's odometry is not starved, and urgent colours are painted first. As a communication design it is weaker than the cited work: it was not evaluated with viewers, it relies on colour alone, two meanings share red, it has no "no data" state when the supervisor is unreachable, and its colour semantics contradict a widely used flight-controller convention.
