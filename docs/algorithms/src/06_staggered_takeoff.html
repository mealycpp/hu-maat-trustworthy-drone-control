1. Purpose and context

After landings the aircraft rest wherever they touched down; two of them may be parked closer than the formation spacing. Launching both simultaneously to the same altitude would place them within the proximity-watchdog distance. Instead of refusing such a take-off, the supervisor computes a layered, staggered launch: aircraft in each close pair are assigned to two altitude layers and to two launch phases. The plan is computed once at command time; release of waiting aircraft happens in the 10 Hz control loop based on telemetry.

2. Inputs, outputs, data structures

  • Inputs: target names; requested altitude (params.altitude, default 1.7 m; the HU route sends 1.65 m); live positions and modes of all five aircraft.
  • Output: plan {name: {alt, wait_for: [names]}} for aircraft in close pairs (empty if none), or a refusal. Each Drone carries queue_after, queue_alt, queue_since and mode QUEUED while waiting.
  • An event STAGGERED_TAKEOFF describes the plan; STAGGER_RELEASE / STAGGER_CANCELLED record outcomes.

3. Algorithm

Algorithm 6.1 PLAN-STAGGER

1function PLAN-STAGGER(targets, params)
2 base ← clamp(float(params.altitude or 1.7), 0.25, 2.6 − 0.90) // ≤ 1.70 m
3 L ← [ n ∈ targets : mode(n) ∈ {READY, GROUNDED, WAITING} ] // aircraft that will launch
4 h(a,b) ← horizontal distance
5 for n in L, for o in fleet, o ≠ n do
6 if mode(o) ∉ PARKED and h(n,o) < 0.88 and z(o) < base + 0.90 + 0.5 then
7 refuse "n would climb within h m (horizontal) of airborne o"
8 adj(n) ← [ m ∈ L, m ≠ n : h(n,m) < 0.88 − 10⁻⁶ ]
9 if all adj empty then return {} // ordinary simultaneous take-off
10 colour ← {}
11 for root in L (fleet order) with adj(root) ≠ ∅ and root uncoloured do
12 colour[root] ← 0; stack ← [root]
13 while stack ≠ ∅ do
14 a ← pop(stack)
15 for b in adj(a) do
16 if b uncoloured then colour[b] ← 1 − colour[a]; push(stack, b)
17 else if colour[b] = colour[a] then refuse "parked too close together to layer" // odd cycle
18 for n in L with adj(n) ≠ ∅ do
19 if colour[n] = 0 then plan[n] ← (alt = base + 0.90, wait_for = [])
20 else plan[n] ← (alt = base, wait_for = adj(n))
21 return plan

6. Complexity

Graph construction O(|L|²); 2-colouring by iterative DFS O(|L| + |E|); airborne check O(|L|·N). With N = 5 this is negligible. Release checks are O(deg) per aircraft per 0.1 s tick.

7. Properties

Guaranteed

  • Every pair of launching aircraft closer than 0.88 m horizontally ends on different layers 0.90 m apart (a proper 2-colouring), or the whole take-off is refused before any setpoint changes.
  • No lower-layer aircraft leaves the ground until all its close neighbours report fresh telemetry at ≥ 1.20 m and are not faulted.
  • Odd cycles of close aircraft (e.g. three mutually crowded) are refused with an instruction to launch individually.
  • A waiting aircraft never launches after its neighbour aborted, faulted or landed, nor after 25 s; STOP and LAND cancel the wait (no hidden take-off).
  • Take-off below an airborne aircraft within 0.88 m horizontally is refused.

Not guaranteed

  • Pairs at exactly or just above 0.88 m horizontal launch simultaneously to the same altitude; their spacing then relies on the controller holding XY during the climb.
  • The upper layer is base + 0.90 m only for coloured aircraft; uncoupled aircraft use max(z+0.2, min(2.6, altitude)), so a requested altitude above 1.70 m produces mixed altitudes.
  • The plan uses positions at command time; drift while waiting is not re-planned.
  • Colour assignment depends on fleet order (deterministic but arbitrary: the first aircraft of each component climbs high).
  • Release depends on the neighbours' altitude only, not on their horizontal drift.
  • A QUEUED aircraft receives neither a twist nor an explicit disarm: the QUEUED branch of the loop ends the tick before the 10 Hz disarm that READY/GROUNDED/WAITING aircraft receive. It was disarmed while parked, so it normally stays on the ground, but the “actively disarmed” property of Algorithm 7 does not cover QUEUED.
  • While the queued aircraft is stale the release rule is not evaluated for it (the telemetry watchdog runs first), and a stale partner fails the release test; queue_since keeps ageing, so a telemetry gap longer than 25 s ends the wait in GROUNDED.
  • Rotor downwash is not modelled (see Section 9).

9. Comparison with alternatives and related work

Launching several aircraft from crowded parking spots is a small instance of multi-robot motion coordination. Established approaches either serialise the robots by priority and plan each one around the trajectories of higher-priority robots, or compute jointly collision-free, time-parameterised trajectories for the whole team. The HU-MA'AT supervisor does neither: it computes only a launch order and two altitude layers, and releases waiting aircraft on observed altitude.

Where ours is weaker. It handles only vertical climbs from rest and only bipartite crowding; it provides no trajectory-level separation guarantee, no downwash model and no timing model; and the colour (which aircraft climbs high) is decided by fleet order rather than by any cost. Where it is adequate. With five aircraft in simulation, the decision is computed in microseconds, is explained by a single event line, and the release is gated on telemetry rather than on an assumed climb time. It does not replace a trajectory planner if the fleet or the parking density grows.
