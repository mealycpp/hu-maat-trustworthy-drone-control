1. Purpose and context

Browser speech recognition mishears the aircraft names (Ra as "rock" or "raw", Horus as "chorus" or "horror") and accented words ("yella" for yalla, "old" for all). Silently rewriting a transcript and then executing it would let a recogniser error choose the aircraft. This algorithm repairs a fixed set of known confusions but never executes a repaired command without a second, separate confirmation, with one deliberate exception: emergency phrases (Algorithm 2), where delay is the larger risk.

2. Inputs, outputs, state

  • Inputs: raw transcript (1..300 chars) on /api/hu/voice-auto; a clarification id on /api/hu/voice-accept; /api/hu/cancel; dashboard review path /api/hu/command with voice_reviewed.
  • State: server: voice_pending, at most one entry {utterance (corrected), heard (raw), at}, id of 12 hex characters; the command table pending of Algorithm 1. Client (hands-free dashboard): one pending object of kind alias or hu with a 45 s timer.
  • Outputs: decision records with band VOICE_REVIEW, VOICE_CLARIFY, EMERGENCY, or the bands of Algorithms 1/3; original_transcript is kept in every record.

Figure 19.1. Flowcharts of Service.voice_auto (left) and Service.voice_accept (right). The entry is popped before the age test, so an expired id is also consumed. A command produced by an accepted correction still passes through all of Algorithms 2, 3 and 1; acceptance of the correction is not authorisation of the command.
Figure 19.2. Dialogue state machine of the hands-free voice front end (server: voice_pending, pending; client: setPending, recognizedYes, recognizedCancel in hu_live_dashboard.html). In CLARIFY, "yes", "yeah", "correct", "that's right", "yes please" or an explicit confirm phrase accepts; in CONFIRM only an explicit phrase ("confirm", "I confirm", "affirmative", ...) authorises, and bare "yes" is not accepted. Any other utterance in either pending state re-prompts (it is not sent), except an emergency phrase, which cancels the pending entry and is dispatched at once. The client timeout (45 s) is shorter than the server lifetimes.

6. Complexity

O(|A|·|u|) for |A| = 20 alias substitutions plus one contextual regular expression.

7. Properties

Guaranteed

  • A transcript changed by normalisation is never dispatched on the same request (except emergency phrases); it requires a separate accept carrying a server-held id within 75 s.
  • Only one clarification can be pending; a newer one replaces it, a used one cannot be replayed.
  • "old" is rewritten only in the listed verb contexts; other uses are untouched.
  • Unreviewed voice input on the dashboard route never reaches model inference.
  • Emergency phrases, including alias-corrected ones ("yella land"), act immediately.

Not guaranteed

  • Common words in the alias list (e.g. rock, thought, yellow, prop) are rewritten wherever they occur; this is safe only because the result must be confirmed (or is an emergency).
  • An uncorrected but misrecognised transcript (e.g. a wrong but valid name) proceeds to normal gating without extra confirmation; protection then comes from Algorithms 1/3 (CONFIRM band for mission proposals; EXECUTE allowed for confident HU primitives).
  • "Yes" and "confirm" are recognised in the browser by exact phrase lists (Figure 19.2); robustness to recogniser errors is not measured. A misrecognised "yes" can accept a correction, but cannot by itself authorise a CONFIRM-band command.
  • Only the first recognition alternative is used and its confidence is ignored, although the dashboard requests three alternatives.
  • The 45 s timeout is client-side. If the page is closed, server entries remain until their 75 s / 90 s lifetimes are exceeded, after which an accept or confirm is refused.

9. Comparison with alternatives and related work

Spoken dialogue systems handle recognition errors with explicit or implicit confirmation, confidence-dependent strategies, or belief tracking; aviation radiotelephony uses read-back. These are compared with the protocol of this document.

  • Explicit and implicit verification (survey [1]): explicit confirmation asks a yes/no question about the recognised content; implicit confirmation repeats it inside the next prompt and lets the user object. Explicit confirmation costs a turn per item.
  • Non-understanding recovery strategies [2]: an empirical study of ten recovery strategies in a deployed spoken dialogue system, including how strategy choice affects recovery and whether a better selection policy can be learned.
  • POMDP dialogue management [3]: a belief over user goals is maintained from N-best recognition hypotheses, and when to confirm is chosen by an optimised policy; hand-crafted strategies are shown to be special cases.
  • Read-back of safety-related instructions (ICAO PANS-ATM, Doc 4444) [4]: the recipient reads back safety-related parts of a clearance and the sender checks the read-back.

Where this protocol is weaker. A transcript that is misrecognised as a different valid command (e.g. the wrong aircraft name spelled correctly) is not confirmed by this layer; protection then rests on the bands of Algorithms 1 and 3. The recogniser's confidence and its other two alternatives (the dashboard requests maxAlternatives = 3) are ignored, and the policy is not learned or evaluated on recorded speech. Where it differs. The only automatic rewriting is a short, published alias table, every rewrite is read back and needs a spoken "yes", accepting a correction never authorises the command itself (a CONFIRM-band result needs a second, explicit "confirm"), and emergency phrases are exempt so that a read-back never delays a stop or landing.

10. Relation to other algorithms

Front end of Algorithm 2 (emergency short-cut) and of the pipeline Algorithm 3 → Algorithm 1. Browser-side timing of voice-to-motion is logged separately (/api/hu/latency, logs/hu_voice_to_motion.jsonl) without influencing decisions.
