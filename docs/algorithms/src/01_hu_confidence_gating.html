1. Purpose and context

HU is the natural-language command interpreter of the HU-MA'AT demo. A frozen pretrained language model (SmolLM2-135M) supplies sentence representations; three small trained heads classify the flight action, decide per aircraft whether it is addressed, and detect compound commands. This algorithm turns those neural outputs into one of three decision bands, EXECUTE, CONFIRM (operator must confirm) or REFUSE, and then applies deterministic guards that can only lower a band (never raise it). The asymmetry is deliberate: a false refusal costs the operator a repeat; a false execution moves an aircraft. The same thresholds are re-checked independently at the flight supervisor's HTTP boundary.

The model path is reached only after the symbolic emergency channel (Algorithm 2) and the deterministic mission router (Algorithm 3) have declined the utterance. In the current routing, the sentences that reach the neural path and can be dispatched are, in practice, plain take-off / land / hover / stop primitives addressed to names, collectives or exclusions; moves, turns and formations are handled by the mission route.

3. Algorithm

Algorithm 1.1 HU-Parse (neural band assignment)
Source: rscl-hu-latest/hu/gateway/hu_service.py: HU.parse, HU._emb, _mentions, extract_params
1procedure HU-PARSE(u)
2 R ← roster() // ordered aircraft names
3 T ← [u] ++ [ "drone: r | index: k (ordinal words) | mentioned: M(r,u) | utterance: u" for k, r in R ]
4 E ← EMB(T) // frozen SmolLM2-135M, truncation 64 tokens
5 // EMB = concat(masked mean, masked max) of last hidden state
6 p_a ← softmax(H_action(E[0])); a ← argmax p_a; c_a ← max p_a
7 comp ← sigmoid(H_compound(E[0])) > 0.5
8 for i in 1..|R| do m_i ← sigmoid(H_match(E[i]))
9 targets ← [ R_i : m_i > τ ] // τ from checkpoint (key "tau"), default 0.5
10 c_t ← min_i max(m_i, 1 − m_i) // weakest per-aircraft decision (1.0 if no aircraft)
11 c ← min(c_a, c_t)
12 if comp then band ← REFUSE // "compound commands: coming online"
13 else if a = REFUSE then band ← REFUSE
14 else if targets = ∅ then band ← REFUSE // no addressee resolved
15 else if c ≥ 0.85 then band ← EXECUTE
16 else if c ≥ 0.55 then band ← CONFIRM
17 else band ← REFUSE
18 params ← EXTRACT-PARAMS(a, u) // symbolic; may set params.range_violation
19 return (a, params, targets, c, band)

M(r,u) (_mentions) is "yes" if the lower-cased name is a substring of u or some token differs from it by at most one character (position-wise mismatches plus length difference, lengths within one), else "no". EXTRACT-PARAMS normalises number words and units (m → cm, ft → cm, inch → cm, min → s), takes the first integer, gates it to a safe range, and snaps it to a bin; an out-of-range value sets range_violation and leaves the parameter empty.

Algorithm 1.2 Bridge guards and band enforcement (neural route only)
Source: festival/hu_live_server.py: Service.command (model branch), explicit_primitive_intent, stated_targets, translate, Service.confirm
20procedure HU-GUARD(u_norm, unrecognized) // reached only if Alg. 2 and Alg. 3 declined u
21 r ← HU-PARSE(u_norm)
22 I ← EXPLICIT-PRIMITIVE-INTENT(u_norm) // lexical candidate set or ∅
23 if unrecognized and r.band ≠ REFUSE then r.band ← REFUSE // no explicit flight command: never execute
24 if I ≠ ∅ and r.action ∉ I then r.band ← REFUSE // command-intent mismatch
25 X ← STATED-TARGETS(u_norm) // None: no explicit address; []: explicit but unresolvable
26 if X ≠ None and set(r.targets) ≠ set(X) then r.band ← REFUSE // named-address guard
27 if r.params.range_violation then r.band ← REFUSE
28 if r.band ∈ {EXECUTE, CONFIRM} then
29 try
30 (act, pr) ← TRANSLATE(r.action, r.params) // raises on any unsupported / out-of-range value
31 require r.targets non-empty and r.targets ⊆ NAMES
32 require 0 ≤ r.confidence ≤ 1
33 if r.band = EXECUTE then
34 require r.confidence ≥ 0.85; dispatch(act, r.targets, pr, r.confidence, confirmed=false)
35 else
36 require r.confidence ≥ 0.55; pending[id] ← (act, r.targets, pr, r.confidence, now)
37 except ValueError or DispatchError: r.band ← REFUSE
38 log r; return r
39procedure CONFIRM(id) // operator action
40 p ← pending.pop(id) // single use
41 if p = None or now − p.at > 90 s then refuse
42 dispatch(p.act, p.targets, p.params, p.confidence, confirmed=true)
Algorithm 1.3 Supervisor-side gate
Source: festival/control_server_hu.py: Handler.do_POST, route /api/hu/dispatch
44procedure HU-DISPATCH(request)
45 if not constant_time_equal(request.X-HU-Token, token_file) then return 403
46 c ← float(request.confidence); conf_ok ← finite(c) and 0 ≤ c ≤ 1
47 if not conf_ok then return 400
48 emergency ← request.symbolic_emergency = true and action ∈ {emergency_land, emergency_hover}
49 if not emergency and (c < 0.55 or (c < 0.85 and not request.operator_confirmed)) then
50 return 409 (decision CONFIRM if c ≥ 0.55 else REFUSE)
51 return Fleet.command(action, targets, params) // all supervisor preconditions still apply

Lexical guards

  • EXPLICIT-PRIMITIVE-INTENT: adds TAKEOFF for take off / launch / lift off; LAND for land / landing / touch down; {STOP, HOVER} for stop / hover / hold; MOVE for forward, back(ward)(s), move, left, right; UP for go up, rise, ascend, up, climb; DOWN for go down, descend, down, lower. Multiple words give a union; the guard only fails when the predicted action is outside the union.
  • STATED-TARGETS (Algorithm 4.2): exact whole-word fleet names; a collective (everyone, everybody, all (the) drone(s), the fleet, the swarm, or plain all followed by except / excluding / but not / and or a primitive verb) gives the whole fleet minus an exclusion list (except / excluding / but not + one or more names separated by commas, and or &). It returns None when no address is stated (the guard abstains), and the empty list, which forces REFUSE, for any address it cannot resolve exactly: an unparseable exclusion, an exclusion without ALL, a name next to ALL that is outside the exclusion list, “All and Ra”, or an exclusion of every aircraft.
  • TRANSLATE: TAKEOFF → takeoff at 1.65 m; LAND → land; STOP and HOVER → hover; MOVE distance must be 10..200 cm, direction forward/back/left/right; UP/DOWN 10..200 cm; TURN 5..180° clockwise/counterclockwise; any other label is refused.

4. Flowchart and state diagram

Figure 1.1. State machine of one decision (Service.pending, Service.confirm, Service.cancel). Entries are single use: pending.pop runs before the age test, so a late or repeated confirm finds nothing and is refused. There is no server-side sweeper; an entry that is never confirmed or cancelled stays in memory until the process restarts (it can no longer be dispatched after 90 s). The 45 s timer is the hands-free dashboard's own timeout, which sends /api/hu/cancel. Mission proposals (Algorithm 3) use the same states with kind = mission and are sent to /api/mission/dispatch.

6. Complexity

One batched encoder forward pass over |R|+1 sequences of at most 64 tokens: O((|R|+1)·L²·d) attention cost with L ≤ 64, plus O(|R|) head evaluations. All guards are regular-expression scans, O(|u|) each. Measured per-parse latency is reported in each decision record (latency_ms); no aggregate is computed here.

7. Properties

Guaranteed by the code

  • Monotone refusal. Every guard after HU.parse can only set the band to REFUSE; none can promote REFUSE or CONFIRM.
  • No dispatch below 0.85 without confirmation, and none below 0.55 at all (outside the symbolic emergency channel): enforced in the bridge and again, independently, at the supervisor (constant-time token check, finite confidence in [0,1]).
  • Joint confidence. The reported confidence is the minimum of the action probability and the weakest per-aircraft address decision, so an uncertain address lowers the band even when the action is certain.
  • Contradiction refusal. If the text explicitly names a primitive verb family, a prediction outside that family is never dispatched, whatever its confidence. If the text explicitly names aircraft or a collective, any different target set is refused rather than repaired. An explicit address that STATED-TARGETS cannot resolve exactly yields the empty expected set, which no non-empty model target set matches (and an empty target set is never dispatched, line 31), so an excluded aircraft cannot be in a dispatched set on this route.
  • Unrecognised sentences never execute: when the mission router marks a sentence as having no explicit flight command, a non-REFUSE model output is overridden to REFUSE.
  • Confirmations are single-use and expire after 90 s.

Not guaranteed

  • The thresholds are applied to softmax/sigmoid outputs; no calibration of these scores is performed or verified in this repository. "Confidence" is therefore a score, not a probability of correctness.
  • When the utterance contains no explicit verb or address, the lexical guards abstain, and the decision rests on the model alone (e.g. "up you go" relies on the trained heads).
  • The TURN class has no lexical intent family; a TURN prediction is constrained only by TRANSLATE bounds. (Turns are normally routed to the mission parser first.)
  • The HOVER duration parameter is extracted but not used by TRANSLATE; hover is an indefinite hold.
  • Exclusion lists in the address guard — FIXED 2026-11-12. The previous revision recognised only the first excluded name and so, for “All except Ra and Thoth, take off”, expected {Ra, Thoth}, the aircraft the operator excluded. STATED-TARGETS now parses multi-name exclusion lists, treats all before except / and or a verb as collective, and returns the empty list (REFUSE) for every form it cannot resolve; for the example it now expects {Horus, Anubis, Osiris}, as Algorithm 4.1 does. Covered by acceptance/tests/test_guard_targets.py (Algorithm 4, Table 4.1). Remaining limitation: the guard still has no hedge-word check of its own (such sentences are refused earlier by Algorithm 3).
  • Physical safety of the dispatched action is not decided here; it is delegated to the supervisor's preconditions (Algorithms 6–9).
  • Roster fallback [Horus, Ra, Thoth] would silently shrink the fleet if the roster file lost its assignments.

9. Comparison with alternatives and related work

Turning a classifier score into execute / ask / refuse is the reject-option or selective-prediction problem. Four established approaches are compared with the gate of this document.

  • Chow's reject rule [1]: with true class posteriors, rejecting whenever the top posterior is below a threshold derived from the costs of error and rejection minimises expected cost. HU's two thresholds are a three-way extension of the same form, but HU's scores are not posteriors (no calibration is performed), so the optimality argument does not transfer.
  • Selective classification with a risk guarantee [2]: the threshold on the maximum softmax response is chosen on held-out labelled data so that the selective error is below a user-set target with stated probability. HU's 0.85 / 0.55 are fixed constants; no risk–coverage curve has been measured for them.
  • Post-hoc calibration (temperature scaling) [3]: one scalar fitted on a validation set makes softmax confidences approximately calibrated. It is not applied to HU's action or match heads.
  • Conformal prediction [4], and its use for language-driven robots in KnowNo [5]: a calibration set yields prediction sets with a distribution-free coverage guarantee (under exchangeability); the robot asks a human whenever the set is not a single option. HU's CONFIRM band plays the same role (ask the operator), without the coverage guarantee.

Where the HU gate is weaker. None of its thresholds has a statistical interpretation, and the error rate of EXECUTE decisions is unknown; [2]–[5] would each require a labelled, representative set of operator utterances, which does not exist in this repository. Where it differs. The lexical intent check, the exact-address guard and the supervisor re-check are independent of the score, so a confidently wrong action label or target set is refused when the sentence itself contradicts it; the score-based methods above do not include such checks. The guards do not help when the sentence contains no explicit verb or address.

10. Relation to other algorithms

Preceded by Algorithm 2 (emergency channel, which bypasses this gate) and Algorithm 3 (routing). Uses address semantics close to, but not identical with, Algorithm 4. Dispatched commands are subject to Algorithms 6–9 in the supervisor. Voice input reaches this gate only through Algorithm 19.
