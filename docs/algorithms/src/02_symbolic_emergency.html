1. Purpose and context

An operator must be able to stop or land the whole fleet without depending on a neural model, a confidence score, an aircraft name or a confirmation dialog. The symbolic emergency channel recognises a small closed set of emergency phrases (English and Arabic-derived khalas, yalla) after deterministic normalisation, and dispatches a fleet-wide hold or landing with a symbolic_emergency flag that the supervisor accepts without the model thresholds of Algorithm 1. It is checked first for every utterance, before mission routing and before the model.

7 if cand ∈ EMERGENCY_LAND ∪ EMERGENCY_HOVER then return cand

15// supervisor side
16procedure SUPERVISOR-EMERGENCY(act) // Fleet.command, under the fleet lock
17 token check; confidence thresholds skipped because symbolic_emergency ∧ act ∈ {emergency_*}
18 targets ← ALL; action ← land (emergency_land) or hover (emergency_hover)
19 for d in fleet: if d.land_latched and d.mode ≠ LANDING then d.land_latched ← false // touched down
20 if action ∉ {land, fault, clear_fault} then // LATCH GUARD, applied to every command
21 L ← { d ∈ targets : d.land_latched }; targets ← targets \ L
22 if L ≠ ∅ then log "EMERGENCY LANDING LATCHED: <ACTION> ignored for L (still landing)"
23 if targets = ∅ then return ok (targets = [], latched = L) // nothing else to do
24 if act = emergency_land then d.land_latched ← true for d in targets // plain land: no latch
25 stale ← aircraft without fresh odometry (age ≥ 2.0 s)
26 targets ← targets \ stale; log SAFETY_SKIPPED for stale // safe-direction: do not block the fleet
27 if targets = ∅ then refuse
28 emergency_hover bypasses the fault block; land is never fault-blocked
29 for d in targets do
30 if action = hover then
31 QUEUED → GROUNDED (cancel staggered launch); parked/FAULT → hold z; else HOVER at max(0.25, z)
32 else // land
33 QUEUED → GROUNDED; parked → unchanged; else fault ← false, target ← (x, y, 0.12), mode ← LANDING

Voice: in voice_auto, if the alias-corrected transcript is an emergency phrase, it is executed immediately (no spoken confirmation of the correction), whereas any other corrected transcript requires a separate confirmation (Algorithm 19). Typed input is never held for review.

4. Flowchart and state diagram

Figure 2.1. Flowchart of the symbolic emergency channel (emergency_key, Service.command, /api/hu/dispatch, Fleet.command). Stale aircraft are skipped and logged as SAFETY_SKIPPED; the request fails only if no target is fresh. “Hover drops latched”: aircraft still in an emergency landing are removed from the targets (latch guard, lines 19–23); if none is left, the request returns ok with no target.
Figure 2.2. The channel itself is stateless (it keeps no memory between utterances); the state it acts on is the per-aircraft mode in the supervisor (Fleet.command, Fleet.loop). The diagram shows only transitions caused by the emergency commands and the touchdown rule. The dashed LANDING → HOVER edge applies only to an ordinary landing. An emergency landing is latched (Drone.land_latched): every later non-landing command naming the aircraft (stop/hover, take-off, move, …) is ignored and logged until the aircraft is no longer LANDING. Aircraft with stale odometry receive no command at all.

6. Complexity

EMERGENCY-KEY performs at most 7 set look-ups on strings of length ≤ 300: O(|u|). Dispatch is O(N) in the number of aircraft (N = 5). No model inference; the live fault scenario recorded an acknowledgement of 3.0 ms (see Section 8).

7. Properties

Guaranteed

  • Independence from the neural model: recognition is exact set membership after deterministic rewriting; no score is involved.
  • Precedence: the check runs before mission routing and model inference for every typed and voice command.
  • Bare land, and any phrase not in the closed set after rewriting, is not an emergency.
  • Safe-direction availability: one aircraft with stale odometry does not block landing or holding the others; the skipped aircraft are logged (SAFETY_SKIPPED).
  • The runtime proximity watchdog never cancels a landing (LANDING is excluded from proximity holds, Algorithm 7), so close aircraft are not frozen in the air during an emergency landing.
  • A land/hold never launches a parked aircraft and cancels queued staggered launches.
  • Emergency landing is latched. Once emergency_land has put an aircraft into LANDING, a later stop/hover (emergency or not), take-off, move, turn or spin naming it is ignored for that aircraft and logged as EMERGENCY LANDING LATCHED: <ACTION> ignored for … (still landing); other named aircraft are still commanded. A formation that includes a LANDING aircraft is refused by its own airborne precondition (Algorithm 5). The latch ends once the aircraft is no longer LANDING (touched down).

Not guaranteed

  • Stale aircraft receive no new command (the control loop sends zero velocity with motors not re-enabled; Algorithm 9); the channel cannot land an aircraft whose telemetry is lost.
  • Recognition depends on the speech recogniser producing a phrase in the set (plus the alias table); paraphrases such as "please put them all down" are not recognised and fall through to Algorithms 3/1.
  • The phrase stop embedded in a longer sentence is not an emergency (only whole-utterance matches after the listed rewrites).
  • An ordinary (non-emergency) land is not latched: a later stop / hover still turns that landing into a hover (Figure 2.2, dashed edge). The simulated fault command is exempt from the latch; applied to a landing aircraft it holds it in FAULT (simulation-only command).
  • Landing is vertical at the current XY; no landing-site deconfliction is performed.
  • Emergency dispatch does not wait for physical confirmation; dispatched reflects the HTTP acknowledgement only.

9. Comparison with alternatives and related work

The channel is a small, trusted path that can override the complex (neural and planning) command path. That is the idea behind the Simplex architecture and run-time assurance (RTA); the industrial counterpart is a hardware emergency stop.

  • Simplex architecture [1, 2]: a verified, simple safety controller runs beside a complex controller; a decision module switches to the safety controller when the plant approaches the boundary of a recoverable region. The switch is automatic and based on the plant state.
  • Run-time assurance standard ASTM F3269-21 [3]: specifies RTA components (monitor, recovery function, switch) and requirements for bounding the behaviour of unassured complex functions in aircraft systems, with assurance levels from a system safety assessment.
  • SOTER [4]: a programming framework in which each RTA module pairs an advanced and a safe controller with a safety specification; well-formed modules carry a formal guarantee. It was evaluated on drone software in simulation and on real vehicles.
  • Hardware emergency stop (ISO 13850:2015) [5]: a dedicated, operator-initiated stop function on machinery, with design principles independent of the energy type; for electrical equipment the realisation is in IEC 60204-1.

Where this channel is weaker. It is not independent in the sense of [1]–[5]: it depends on the speech recogniser (for voice), the browser, the HU bridge process, the token file, the local HTTP link and the supervisor process, and it cannot reach an aircraft whose odometry is stale. It does not monitor anything by itself. A real-vehicle deployment would need a separate stop path (e.g. a hard-wired or radio kill switch) that does not pass through any of this software. Where it is useful. Within the simulation it gives the operator a model-free override with a measured 3.0 ms acknowledgement, and it removes the confidence threshold from the safe-direction action, as RTA recovery functions do.
