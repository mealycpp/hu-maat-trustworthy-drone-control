1. Purpose and context

The supervisor converts mode + setpoint into velocity commands for the Gazebo multicopter velocity controller and decides when a manoeuvre is complete. Completion matters for safety and usability: subsequent single-aircraft commands require HOVER (Algorithm 7.2), group moves require "settled" members (Algorithm 8), and the mission coordinator verifies steps from these modes (Algorithm 11). A former defect (aircraft remaining in MOVE forever, so that every following move was refused) is fixed by the arrival rule described here. The same loop implements the telemetry watchdog that withholds motion from aircraft whose odometry is stale.

2. Inputs, outputs

Inputs per tick: position p, velocity v, yaw ψ (from quaternion), setpoint (x*, y*, z*, ψ*), mode, odometry receive time. Outputs: body-frame linear velocity (bx, by), vertical velocity vz, yaw rate rz with motor enable; mode transitions and events HOVER, ARRIVED, SPIN_COMPLETE.

6. Complexity

O(1) per aircraft per tick; O(N) per tick overall (plus the O(N²) watchdog of Algorithm 7).

7. Properties

Guaranteed

  • Commanded velocities are bounded (0.62 m/s per horizontal axis, i.e. ≤ 0.88 m/s horizontal; 0.45 m/s vertical; 0.55 rad/s yaw).
  • A MOVE or TURN is reported complete only when position, speed and yaw are simultaneously within tolerance at one tick; a completed manoeuvre always returns to HOVER, so consecutive relative commands are accepted.
  • No new motion is commanded to an aircraft with stale odometry; motors are not re-enabled for it.
  • Stale aircraft never block a fleet-wide land/hover of the fresh aircraft; they do block (fail closed) every risk-increasing action naming them, and every formation.

Not guaranteed

  • The tracking law has no integral term and no stability proof is given here; arrival may never trigger if a steady-state error ≥ 0.06 m persists (no timeout in the supervisor; Algorithm 11 adds timeouts).
  • Arrival is a single-tick test (no dwell), so a transient pass through the tolerance can end a manoeuvre early.
  • Per-axis saturation distorts straight-line paths (see Algorithm 5 limitations).
  • FORMATION never transitions automatically; "formed" is judged externally (Algorithms 11, 15, 16).
  • "Zero velocity without enable" for a stale aircraft relies on the simulator's controller behaviour; the real state of a stale aircraft is unknown.
  • The yaw-segment logic of SPIN counts segments only when the error is small; a stalled segment stalls the spin.

9. Comparison with alternatives and related work

Deciding that a manoeuvre is “done” is a settling or acceptance criterion. Control engineering defines settling time as the time after which the response enters and stays within a band (typically 2 % or 5 % of the final value) [1], [2]. Autopilots and navigation stacks use simpler acceptance tests on position, heading and speed [3], [4], [5].

Where ours is weaker. There is no dwell or hysteresis, no timeout in the supervisor (an aircraft that never meets the tolerance stays in MOVE), FORMATION has no completion test at all, and the tolerances are not derived from the controller's measured noise. The mission coordinator compensates partly by requiring the completion condition in 3 consecutive 0.25 s samples and by per-action timeouts (Algorithm 11), which is a settling criterion in the classical sense. Where it is adequate. In the noise-free simulator the single-tick test has been sufficient for every recorded motion test.

10. Relation to other algorithms

Executes the setpoints produced by Algorithms 2, 5, 6, 8; runs after the watchdog (Algorithm 7) in the same tick. Its mode semantics are relied on by Algorithms 10, 11, 15, 16 and recorded by Algorithm 17.
