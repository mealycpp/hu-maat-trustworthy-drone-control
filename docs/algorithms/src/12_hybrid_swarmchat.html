1. Purpose and context

SwarmChat lets visitors and operators talk to the five aircraft as personas in the SpaceOps dashboard. The design separates understanding (a learned intent router), facts (deterministic telemetry engine), wording (an optional small local instruct model, checked by Algorithm 13) and authority (none: chat never reaches a flight endpoint). This document specifies the router and the dispatch logic.

2. Inputs, outputs, data

  • Input: message (1..350 chars), recipient ∈ {FLEET, Horus, Ra, Thoth, Anubis, Osiris}, a copied telemetry snapshot, recent events (35), online flag, per-aircraft health series (Algorithm 17).
  • Router output: {intent, best, confidence, top3, latency_ms, source}; intent = uncertain if confidence < 0.55.
  • Intents (11): social, banter, user_feelings, meta, joke, status, relation, history, followup, command, impossible.
  • State: bounded conversation memory turns (deque, 12) and last = {intent, utterance, recipient, speakers, replies}; persona rotation counter.
  • Output: list of chat messages, each with speaker, role, text, evidence and a source label (TELEMETRY_FACT, UNKNOWN, CHAT_LOCAL_LLM, RULES_PERSONA, SAFETY_SUPERVISOR, MISSION sources).

8procedure TRAIN(seed 0)

11 over dropout(Z, 0.25); report held-out accuracy, confident accuracy/coverage at 0.55,

4. Flowchart and state machine

Figure 12.1 is the control flow of one call to HybridChat.ask, drawn from the code (branch order as implemented: input validation, mission-objective grammar, router, availability fallback, follow-up test, intent dispatch). Figure 12.2 is the only state the module keeps between messages: the record of the previous turn used for follow-ups.

Reading the diagrams. “Previous turn” means self.last is set; the follow-up cue is intent = followup, or (≤ 6 words and a leading and / what about / how about / so / but / why / really / explain / tell me more / go on and intent ∈ {uncertain, meta, followup, social}). The rules-engine branch and the mission branch also set last (intent rules or mission); a later re-ask of such a turn is dispatched as uncertain, because only the eleven router intents are carried over.

6. Complexity

Routing: one encoder pass (≤ 64 tokens) and an 11-way linear layer. Social/history replies: up to two generation calls of ≤ 60 new tokens each, serialised by a single worker. A mission objective triggers the coordinator's planning cost (Algorithm 11, ≤ 14 dry runs).

7. Properties

Guaranteed

  • No actuation path: the module and its HTTP route only append chat messages; the command intent produces a refusal and a preview; mission objectives are planned, never executed.
  • Graceful degradation: if the router or the wording service is unavailable, answers come from the deterministic engine; if generated text is rejected, the deterministic fallback text is used and the rejection reason is recorded.
  • Status and relation answers are produced by the deterministic engine from telemetry, not by the language model.
  • Every message carries a provenance label distinguishing learned wording from facts and rules.

Not guaranteed

  • Intent classification can be wrong; the confident-accuracy figure below is on a small held-out set written by the developers.
  • Generated wording is constrained only by the validator (Algorithm 13); accepted text can still be awkward or vague.
  • Follow-up detection is heuristic (word lists and length) and session state is global to the SpaceOps process (not per user).
  • Mission-objective detection is attempted before routing, so an objective-like sentence always triggers a (read-only) planning call.

  • Router held-out evaluation, from the checkpoint metadata logged at service start (logs/chat_llm/*.jsonl, event ROUTER_LOADED; trained 2026-11-11T05:43:11Z, seed 0): 47 test items, accuracy 0.872; accuracy when confident 0.917 at coverage 0.766 (threshold 0.55); command false positives 0, false negatives 0.
  • Deterministic engine: acceptance/tests/test_swarmchat.py (18 tests, run by run_swarmchat_tests.sh / run_chat_unit.sh). The hybrid dispatch logic in swarmchat_hybrid.py has no dedicated unit test in acceptance/tests; it is exercised by acceptance/chat_probe.py, human_chat.py and swarmchat_transcript.py (no recorded results found). Results of the chat unit runners are not recorded here.

9. Relation to other algorithms

Shares the frozen encoder and pooling with Algorithm 1 (separate head and checkpoint). Uses Algorithm 13 for every generated sentence, Algorithm 17 for history answers, Algorithm 11 for PLAN-ONLY mission discussion, and Algorithm 3 for the read-only command preview. Messages from Algorithms 14 and 15 appear in the same chat stream with their own source labels.

10. Comparison with alternatives and related work

SwarmChat combines three ideas that exist separately in the literature: classifying an utterance into an intent before deciding how to answer, conditioning a generator on external evidence, and placing a programmable check between the generator and the user. The table compares the design with established representatives of each idea. The comparison is qualitative; none of the alternatives was run on the SwarmChat data.

ApproachHow it worksWhere it is stronger than SwarmChatWhere SwarmChat differs
Retrieval-augmented generation (RAG) [1]A retriever selects passages from a large corpus; a sequence-to-sequence generator conditions on them, end to end trained.Open-domain coverage; retrieval over documents; learned joint training; widely evaluated on knowledge-intensive benchmarks.No retrieval: the “evidence” is a small structured record built deterministically from live telemetry, plus an optional deterministic draft. The domain is closed (five aircraft, one arena). Generation is post-checked (Algorithm 13); RAG by itself does not guarantee that the output stays within the retrieved content.
Pipeline NLU + dialogue manager (e.g. Rasa NLU/Core) [2]Intent classifier and entity extractor feed a trained or rule-based dialogue policy that selects the next action; tracker stores slots and history.Entity/slot extraction, trained dialogue policies, form filling, mature tooling and per-user conversation trackers.Same split of understanding and action selection, but SwarmChat has only an 11-way intent head on a frozen encoder, no entity model (names found by regular expressions), a hand-written dispatch table and a single global follow-up state (Figure 12.2) rather than per-user trackers.
Programmable guardrails (NeMo Guardrails) [3]A runtime with a dialogue-flow language defines input, dialogue and output rails around an LLM; rails can call checks or block topics.Declarative, reconfigurable rails; topic control; reusable across models and applications; documented evaluation.The rails here are code, not configuration: the module has no flight endpoint at all (a structural rather than a policy guarantee), commands always get a refusal and a read-only preview, and every generated sentence passes the validator of Algorithm 13. Changing a rule requires a code change and re-test.
Template / data-to-text NLG with content planning [4]A content plan selects which records to mention; a generator (neural or template) realises them.Explicit content selection and ordering; learned fluency over many records (e.g. sports statistics).Facts (status, relation, history drafts) are produced by templates in the deterministic engine; the language model only rephrases. Content selection is fixed per intent rather than learned.
Where this design is weaker. The router is a single linear layer trained on 288 developer-written sentences; its held-out set (47 items) was written by the same people, so its accuracy is optimistic for visitors. Follow-up detection relies on word lists and a 6-word length test and has no notion of who is asking. There is no retrieval over documentation, so architecture answers are limited to the six fixed statements in ARCHITECTURE. Compared with the systems above, there is no published evaluation, no per-user state and no configuration language for the rules.

Honesty notes. The wording model produces persona-styled text; it does not reason about the mission, and the personas are wording only (same controller, same facts). Messages labelled TELEMETRY_FACT come from templates, not from the model. Chat cannot actuate: the module contains no call to a flight endpoint, and mission objectives are planned read-only and must be approved and launched from the console.
