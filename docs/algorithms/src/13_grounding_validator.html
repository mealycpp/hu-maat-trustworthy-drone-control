1. Purpose and context

A small local instruct model rewords SwarmChat replies in each aircraft's persona (Algorithm 12). Small models invent numbers, aircraft, events and authority ("I'll take off now"). The validator is the gate between the model and the operator: a generated sentence is shown only when validate() returns no violations; otherwise the deterministic text is shown. The design principle is asymmetric: a false rejection costs style, a false acceptance could put an invented fact in front of the operator. The validator is pure standard-library Python, so the observer process can re-check text independently of the model process.

2. Inputs and outputs

validate(text, speaker, evidence, allowed_facts, draft, history, user_text, persona, require_draft_facts=True) → list of violation strings "code: detail" (empty = accepted). Support sets: numbers and strings found by recursively walking evidence (depth ≤ 8), numbers in allowed_facts and the draft. User text and history support names but never numbers or shapes.

43 // busy queue, timeout, not loaded → {fallback: true, reason}; caller shows deterministic text

The standard repetition penalty divides (or multiplies, for negative logits) the logit of every token already present in the sequence, including the prompt. Here the prompt contains the grounded facts and the draft, so the stock penalty pushes the model away from exactly the numbers it must repeat. prompt_ignore_length = P restricts the penalty to tokens generated after the prompt.

4. Flowchart and state machine

The validator is a pure function: it keeps no state between calls, and the same text and evidence always give the same verdict. Figure 13.1 is therefore a flowchart of one call, with the decision that the service and SwarmChat take on its result. The state that does exist belongs to the generation service around it, whose bounded queue and deadlines decide whether a sentence reaches the validator at all (Figure 13.2).

Data flow. SwarmChat (Algorithm 12) builds evidence (telemetry fields, recorder history, fixed architecture statements) and, for history and follow-up replies, a deterministic draft. The service turns both into the prompt, samples at most 60 new tokens, cleans the text and calls validate with the same evidence and draft. User text and chat history are passed too, but they can only make names acceptable, never numbers or shapes.

6. Complexity

Validation is O(|t| + |support|) per regular expression with a fixed set of patterns, plus O(|numerals(t)|·|N|) for numbers and O(|fleet|·|support|) for names; sub-millisecond to milliseconds for chat-length texts. Generation dominates (≤ 60 new tokens on CPU).

7. Properties

Guaranteed

  • An accepted sentence contains no numeral that is not equal to, or a permitted rounding of, an evidence/draft/allowed number; no fleet name unknown to the conversation; no shape word unsupported by evidence in a formation context; and none of the listed authority, feelings, identity, event, world or contradiction patterns (outside negation and verbatim-draft exemptions).
  • User text and history never make a number or a shape "supported".
  • Deterministic and side-effect free; the same text and evidence always give the same verdict.
  • Rejected or unavailable generations are replaced by deterministic text; the decision and reasons are logged append-only.

Not guaranteed

  • Pattern-based: semantic falsehoods expressed without a flagged numeral, name, shape or keyword (e.g. a wrong comparison "Ra is higher than Thoth" when both values are in evidence) are not detected.
  • Spelled-out numbers are not checked. Negation detection is a word-window heuristic and can be fooled.
  • The draft exemption trusts the deterministic draft entirely.
  • The repetition-penalty change affects style and fact retention statistically; it guarantees nothing per sentence.

10. Comparison with alternatives and related work

Detecting unsupported content in generated text is an active research area, usually called hallucination detection or faithfulness evaluation [1]. The validator belongs to the simplest family: lexical checks of the output against a known source. The table places it next to established alternatives. No alternative was run on the SwarmChat logs; the comparison is qualitative and based on the published descriptions.

ApproachHow it worksWhere it is stronger than this validatorWhere this validator differs
Sampling-based self-consistency (SelfCheckGPT) [2]Samples several answers from the same model and scores each sentence by its consistency with the others (BERTScore, QA, n-gram, NLI or prompt variants); no external source needed.Works without any evidence record; catches semantic errors that contain no flagged token; graded scores rather than a binary verdict.Here the source of truth is known exactly (the evidence record), so support can be checked directly and deterministically. Self-consistency needs several generations per reply, which a single-worker CPU service with a 14 s budget cannot afford, and a consistently wrong model passes it.
Atomic-fact verification against a knowledge source (FActScore) [3]Splits the text into atomic facts and checks each one against a source, by humans or by a retriever plus a strong LM.Semantic checking of arbitrary claims, including comparisons and relations; a precision score per text.No decomposition model and no second LM: the validator checks tokens (numerals, names, shape words, keyword patterns). It cannot detect a wrong statement that uses only supported tokens (e.g. swapping which aircraft is higher).
Table-grounded overlap metrics (PARENT) [4]Data-to-text evaluation that aligns n-grams of the output with the source table as well as the reference, giving precision and recall.Continuous score, recall as well as precision, validated against human judgements on WikiBio.Used here as a run-time gate, not an evaluation metric. Only precision-like support is enforced (plus missing_draft_fact as a narrow recall check); there is no score, only accept/reject.
Programmable output rails (NeMo Guardrails) [5]Output rails run checks on a reply before it is returned; the toolkit describes, among others, fact-checking and hallucination rails that use an LLM.Configurable, model-independent framework with several ready-made rails.Same placement in the pipeline, but the checks are fixed Python patterns with no LLM in the loop, so the gate is deterministic, fast and testable, and can be re-run independently by the observer process.

The repetition-penalty change is related to the penalised sampling introduced with CTRL [6], which discounts every token already present in the context; restricting it to generated tokens (prompt_ignore_length) keeps the penalty from discouraging the copying of evidence numbers.

Where this design is weaker. It is purely lexical. It misses false comparisons and relations built from supported tokens, spelled-out numbers, paraphrased incidents not in its keyword lists, and anything the deterministic draft gets wrong (the draft is trusted). Negation handling is a 6-word window. The rule set was tuned on a small number of observed failures and a 35-prompt single-scorer benchmark; unlike the methods above it has no published evaluation against human labels, and its false-rejection rate (11 of the 24 completed generations in the logged sessions, 46 %, were rejected) is high.

Honesty notes. An accepted sentence is not shown to be true; it is shown to contain no unsupported numeral, name, shape word or flagged pattern. The validator does not make the wording model reason, and generated chat cannot actuate anything (Algorithm 12).
