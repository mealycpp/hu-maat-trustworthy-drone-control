1. Purpose and context

The coordinator turns a high-level objective ("inspect north sector", "survey the arena", "form a wedge and hold", "relay chain to east", with constraints such as "keep Ra in reserve", "use three drones", "without Thoth", "in a V formation", "offset 1.2 m") into an ordered list of ordinary supervisor commands. The five "agents" are deterministic rule functions over telemetry (no learning, no language model). Safety authority stays with the supervisor: the plan is validated by Algorithm 10 and executed through the authorised mission gateway only after explicit operator approval.

2. Inputs, outputs, data structures

  • Objective (≤ 200 chars) parsed by parse_objective to {kind ∈ inspect/survey/relay/hold, sector, shape, constraints{reserve, exclude, count, shape, offset_m}}.
  • Snapshot: GET /api/state normalised per aircraft; simulated battery (100 % − 2 %/min of observed airborne time, z > 0.3 m), labelled SIMULATED_ESTIMATE.
  • Bid per agent: available ∈ {YES, NO, UNKNOWN}, reasons, position, distance to sector point, battery, evidence references (field, value, sample time, route).
  • Plan: steps S1..Sk with labels, MA'AT check result, assignment, transcript, four graphs (mission DAG, assignment, proximity, provenance), status ∈ {NOT_PLANNABLE, VALIDATED, REJECTED}, executable=false. Logged to logs/missions/<mission_id>.jsonl.
  • Execution report: per step precheck, dispatch, observed outcome; status COMPLETED / STOPPED / NOT_STARTED, contingency hold.

5 for each agent n: bid_n ← BID(n)
6 stale → UNKNOWN; fault or FAULT → NO; mode ∈ BUSY → NO; mode not plannable → NO;

12 steps ← [takeoff(parked team members, altitude 1.7)] if any parked; steps += [formation(team, shape)]
13 chk ← PLAN-CHECK(steps) // Algorithm 10; failure to reach it ⇒ REJECTED
14 if chk.ok and kind ∈ {inspect, relay, survey} then offset ← SECTOR-OFFSET(obj, chk.goals of formation)
15 else if explicit offset then offset ← unit(sector) · offset_m
16 if kind = survey then a ← offset.y; steps += [move(0,−a), hover 6 s, move(0, 2a), hover 6 s, move(0,−a)]
17 else
18 if offset ≠ 0 then steps += [move(offset)]
19 steps += [hover(8 s if inspect else 6 s)]; if offset ≠ 0 then steps += [move(−offset)]
20 if end = land then steps += [land(team)]
21 chk ← PLAN-CHECK(steps)
22 assignment ← supervisor's formation goals (authoritative) mapped to centred slots; agent prefs recorded
23 if chk.ok then status ← VALIDATED (executable stays false)
24 else status ← REJECTED; if top level then ALTERNATIVES(...)
25function SECTOR-OFFSET(obj, goals)
26 if survey then return (0, 1.0); if explicit offset then return unit·offset // not clamped: MA'AT judges
27 if sector = center or no goals then return (0,0)
28 ext ← max_g (g · unit); o ← max(0, min(1.6, 2.0, 3.10 − ext)); o ← floor(20·o)/20
29 return unit · o
30function ALTERNATIVES(obj, failure) // bounded: first 6 candidates, each fully re-planned
31 candidates, ordered by the failure reason:
32 drone problem (fault|telemetry|must|settled|maneuvering|is MODE;) → exclude each named participant first
33 move/arena/bounds/"within 1.0 m" → drop explicit offset; offsets 0.6× and 0.3× of current if ≥ 0.2 m
34 formation or move failure → shapes v, line, wedge, arc, grid, column, inverted_v (≠ current)
35 otherwise exclusions last
36 return first VALIDATED alternative (needs its own approval), else all tried
Algorithm 11.2 NEGOTIATE (bounded nearest-slot claims)
Source: festival/mission_coordinator.py: negotiate, AgentPolicy.claim_slot
38function NEGOTIATE(team, C)
39 agreed ← {}; pending ← team
40 repeat at most |team| + 1 rounds while pending ≠ ∅
41 claims ← for each n ∈ pending: nearest free slot k (XY distance, rounded to 0.01 m; ties by slot index)
42 pending ← ∅
43 for each slot k (ascending) do
44 winner ← min over claimants by (distance, fleet index); agreed[winner] ← k
45 every other claimant yields (message states the distance difference or the tie rule); pending += loser
46 return agreed
Algorithm 11.3 EXECUTE
Source: festival/mission_coordinator.py: Coordinator.execute, _verify, _done, _abort
47procedure EXECUTE(plan, approve)
48 if approve ≠ true then log EXECUTION_REFUSED; return NOT_STARTED
49 if plan.status ≠ VALIDATED then return NOT_STARTED
50 for i, step in steps do
51 repeat pre ← PLAN-CHECK(steps[i..]) // re-check against the live state
52 until pre.step0.ok or reason ∉ {settled, maneuvering, wait for stable} or 8 s elapsed (poll 0.5 s)
53 if not pre.step0.ok then ABORT(dispatched = false)
54 dispatch step via /api/mission/dispatch (token, operator_confirmed, planner HU-MISSION-COORD)
55 if HTTP ≠ 200 or not ok then ABORT(dispatched = false)
56 obs ← VERIFY(step, pre.step0.planned_goals, timeout[action])
57 if not obs.ok then ABORT(dispatched = true)
58 return COMPLETED
59function VERIFY(step, planned, timeout) // poll every 0.25 s
60 loop
61 track min 3D separation among fresh aircraft with z > 0.3
62 if any target stale or faulted then fail
63 if min separation < 0.82 then fail
64 if action ∈ {formation, move} and ‖live target − planned goal‖ > 0.35 for a target then fail // e.g. SEPARATION_HOLD
65 stable ← stable + 1 if DONE(step) else 0; if stable ≥ 3 then break
66 if elapsed > timeout then fail
67 if dwell_s > 0 then for dwell_s: fail if any target stale, faulted, not HOVER, or drift > 0.30 m
68 return ok
69DONE: takeoff — HOVER, z > 0.8, |z − planned z| < 0.2; formation — FORMATION and within 0.10 m of setpoint;
70 move — HOVER and within 0.10 m; hover — HOVER; land — GROUNDED/READY and z < 0.3
71procedure ABORT(dispatched)
72 if dispatched and action ≠ land then
73 hover all fresh airborne aircraft via the mission gateway; if refused then emergency_hover (Alg. 2)
74 report STOPPED with re-planning options

6. Complexity

Planning: two PLAN-CHECK calls (each dominated by formation assignment, Algorithm 5) plus, on rejection, up to 6 further full plans: ≤ 14 dry runs. Negotiation: ≤ |team|+1 rounds of O(|team|·|C|). Execution: one dry run per step attempt plus polling; wall time is dominated by flight time and timeouts.

7. Properties

Guaranteed

  • Nothing is dispatched without both a VALIDATED status and explicit approval (approve is True); chat and planning paths never call EXECUTE.
  • Each step is re-validated against the live state immediately before dispatch, through the supervisor's own code; MA'AT unavailability fails closed (REJECTED).
  • Completion is judged from telemetry, not acknowledgements; a step must hold its completion condition for 3 consecutive samples.
  • On any deviation after dispatch the fleet is commanded to hold, escalating to the symbolic emergency hover if the hold is refused.
  • Only catalogue shapes with status VALIDATED can be planned. Planning is deterministic for a given snapshot (test test_plan_is_deterministic).
  • The supervisor's assignment overrides the agents' negotiated slots; the transcript states this explicitly.

Not guaranteed

  • "Agents", "bids" and "negotiation" are deterministic rules; the negotiation result does not influence the flown assignment.
  • Battery values are simulated estimates, not measurements.
  • Verification samples at 0.25 s; transient violations between samples are not seen. Aborting does not undo partial effects.
  • Alternative search is bounded and heuristic; failure to find one does not mean none exists.
  • A plan validated now may become invalid later; only the per-step re-check protects execution.

9. Comparison with alternatives and related work

Multi-robot task allocation is classically done by market mechanisms: the contract net protocol (announce, bid, award) [1], auction algorithms for the assignment problem [2], and decentralized consensus-based auctions such as CBBA [3]. In the taxonomy of [4], formation-slot assignment is a single-task-robot, single-robot-task, instantaneous assignment (ST-SR-IA) problem, which reduces to the linear assignment problem. The HU-MA'AT coordinator borrows the vocabulary (bids, negotiation) but is a centralized deterministic rule set whose authoritative assignment comes from the supervisor.

ApproachMechanismWhat it guarantees (under its assumptions)Compared with ours
Contract net protocol [1]A manager announces a task, contractors evaluate and bid, the manager awards a contract; contractors may sub-contract.A general negotiation protocol for distributed problem solving; no optimality claim.Ours: bids are availability flags with reasons and a distance; the coordinator selects the team (closest to the sector point); there are no contracts or sub-contracting.
Auction algorithm [2]Bidders raise prices on their best objects by the bid increment; a relaxation method for the dual of the assignment problem.Terminates with an assignment within n·ε of optimal; parallelisable.Ours: the agents' nearest-slot negotiation is greedy (not optimal) and only recorded; the flown assignment is the supervisor's exhaustive permutation search with separation constraints (exact for ≤ 5 aircraft, factorial cost).
CBBA [3]Each agent builds a bundle of tasks by greedy bidding, then resolves conflicts through local consensus with neighbours.Converges to a conflict-free assignment with a performance guarantee for diminishing marginal gains; tolerant of inconsistent situational awareness.Ours is centralized in one process with one telemetry snapshot; no communication model, no robustness to message loss, no decentralization.
HU-MA'AT coordinator (this document)Closed objective grammar → deterministic bids → recorded negotiation → MA'AT dry run → operator approval → verified execution.Properties of Section 7 (no dispatch without VALIDATED + approval; per-step live re-check; telemetry-verified completion).—

Where ours is weaker. Allocation is centralized (single point of failure), uses distance as the only cost, does not re-allocate during execution (it stops and the operator re-plans), and its “negotiation” has no influence on the outcome. The alternative search is a bounded heuristic. What it adds. Every decision carries telemetry evidence and a source label, safety authority stays with the supervisor's own code path, and the human approval gate is enforced in code. These are properties the market-based methods above do not address, and they are the reason the market vocabulary is used here only descriptively.

10. Relation to other algorithms

Uses Algorithm 5 (slot geometry), Algorithm 10 (validation), and through the gateway Algorithms 6–9; escalates through Algorithm 2. SwarmChat (Algorithm 12) can show a plan (PLAN ONLY) but never executes it.
