1. Purpose and context

Higher-level planners (the mission coordinator, Algorithm 11) need to know, before anything moves, whether a sequence of commands would be accepted by the flight supervisor and what separations it would plan. Re-implementing the supervisor's checks in the planner would risk divergence. MA'AT plan check instead executes the same command() / formation() / _plan_stagger() / _plan_group_move() code on a detached copy of the fleet whose publisher is disabled. The first step is therefore validated exactly as a real command would be at that instant; later steps are validated on a predicted state.

2. Inputs, outputs, data structures

  • Input: steps: non-empty list (≤ 12) of {action, targets, params}, action ∈ {formation, turn, spin, move, takeoff, land, hover}.
  • _PlanScratch: subclass of Fleet with deep-copied Drone objects, private lock, no Gazebo node, no event log, fresh() frozen to the set of aircraft fresh at the snapshot instant, and publish() that raises.
  • Output: {ok, read_only: true, checked_utc, snapshot_monotonic, telemetry (per aircraft x,y,z,v,mode,fault,fresh,age_s,target), steps: [...]}; each step: index, predicted, ok, checked, reason, planned_targets, planned_goals, pairwise_min_sep, planned_min_sep, optional staggered_wait_for, skipped_stale, formation_offset_m, shape.

3. Algorithm

Algorithm 10.1 PLAN-CHECK

1function PLAN-CHECK(steps)
2 require steps is a non-empty list with |steps| ≤ 12
3 with fleet lock: t ← now; F ← { n : fresh(n) }; snap ← deepcopy(drones) // atomic snapshot
4 scratch ← _PlanScratch(snap, F); failed ← false
5 for i, step in enumerate(steps) do // outside the live lock
6 entry ← {index: i, predicted: i > 0}
7 if failed then entry ← not checked ("an earlier step was rejected"); continue
8 validate shape of step (action ∈ PLAN_ACTIONS, targets ⊆ NAMES non-empty, params object)
9 before ← positions and modes in scratch
10 try
11 res ← scratch.command(action, targets, params) // unchanged supervisor code
12 entry ← ok + DESCRIBE(before, res); SETTLE(scratch)
13 except ValueError, TypeError, OverflowError, KeyError as e: entry ← not ok, reason e
14 if not entry.ok then failed ← true
15 return {ok: not failed, read_only: true, telemetry, steps}
16function DESCRIBE(before, res)
17 goal_n ← (x, y, queue_alt) if n QUEUED else (target_x, target_y, target_z) for n ∈ res.targets
18 start_n ← before_n; end_n ← goal_n if n targeted else start_n
19 for each pair (a, b) of the five aircraft do
20 if both are parked (z < 0.30) at start and end then skip
21 best ← ∞
22 for phase in (A, B), for k = 0..40, f = k/40 do
23 g(n) ← (f if phase = B else 0) for queued n; (f if phase = A else 1) otherwise // A: movers; B: queued climb
24 best ← min(best, ‖lerp(start_a, end_a, g(a)) − lerp(start_b, end_b, g(b))‖)
25 pairwise[a|b] ← best
26 return goals, pairwise, planned_min_sep = min(pairwise)
27procedure SETTLE(scratch) // predicted completion
28 QUEUED → at (x, y, queue_alt), HOVER; TAKEOFF/MOVE/TURN/SPIN/FORMATION → at setpoint, yaw = target yaw,
29 mode HOVER (FORMATION stays FORMATION); LANDING → z = 0.05, GROUNDED; all velocities ← 0

4. Data-flow diagram and flowchart

No state machine. plan_check keeps no state between calls: each call takes its own snapshot, builds a scratch copy, and discards it on return. The only mode mapping it applies is the deterministic SETTLE prediction (QUEUED → HOVER at queue altitude; TAKEOFF, MOVE, TURN, SPIN → HOVER at the setpoint; FORMATION stays FORMATION at the setpoint; LANDING → GROUNDED at z = 0.05 m; all velocities zero). The data-flow diagram therefore shows what is read and what can never be written.

Figure 2. Flowchart of Fleet.plan_check. Step 0 runs on the exact snapshot; every later step runs on the state predicted by SETTLE. After the first rejection, later steps are reported but not checked.

6. Complexity

Per step: the cost of the command itself (dominated by formation assignment, Algorithm 5: up to ~8·105 distance evaluations with a shifted formation) plus DESCRIBE: C(5,2) = 10 pairs × 82 samples. Deep copy O(N). The live lock is held only for the snapshot.

7. Properties

Guaranteed

  • Read-only: the scratch object owns copies; any attempt to publish raises; no event is logged; the live state is never mutated.
  • Exactness of step 0: it is validated by the identical code path and the identical state (positions, modes, faults, freshness) a real command would see at the snapshot instant, including refusal messages.
  • Fail-fast: after the first rejected step, later steps are reported "not checked" rather than evaluated on an invalid state.
  • The 10 Hz control loop is not stalled by the (possibly slow) permutation search.

Not guaranteed

  • Steps after the first are validated on an idealised settled state (every setpoint reached exactly, zero velocity); real arrival errors and timing differ.
  • Freshness is frozen: an aircraft fresh at the snapshot is assumed fresh for all predicted steps.
  • The separation report is a straight-line, synchronised, sampled prediction (two phases for staggered take-off); it does not model the controller (Algorithm 9) and is informational: acceptance depends only on the supervisor's own checks.
  • Between the dry run and a real dispatch the world may change; callers must re-check immediately before dispatch (Algorithm 11 does).

9. Comparison with alternatives and related work

Checking a plan before execution and monitoring it during execution are established topics: plan validators check a plan against a formal domain model [1]; runtime verification checks execution traces against formal properties [2], including on robot middleware [3]; verified runtime monitors carry a proof from a hybrid-system model to the running system [4]; runtime-assurance architectures switch to a verified safe controller when a monitor predicts a violation [5], [6]. MA'AT plan check is a dry run of the real implementation, not a check against a model.

Runtime verification [2], ROSRV [3]Monitors synthesised from formal properties observe the running system (for ROSRV: ROS messages) and flag or block violations.Sound detection of violations of the specified property on the observed trace.Ours checks before dispatch; the runtime monitors in HU-MA'AT (watchdog, coordinator VERIFY) are hand-written, not synthesised from a specification.
Verified runtime validation, ModelPlex [4]Monitors derived by proof from a verified hybrid-system model; passing the monitor implies the model's safety proof applies.Safety proof transfers to the execution as long as monitors pass.Ours has no proof at any level; separations are sampled straight-line predictions.

Where ours is weaker. No formal semantics, no proof, no coverage of timing or controller behaviour, frozen freshness, and predicted separations that comparable live data show can be optimistic by 0.18 m without and 0.25 m with proximity holds (Section 8). What it does provide. Agreement by construction between what is checked and what would be executed for the first step, which a separately written validator cannot provide, at no modelling cost.

10. Relation to other algorithms

Wraps Algorithms 5–9 (command path) without modification; is the validation authority ("MA'AT") for Algorithm 11 and is replayed offline by OfflineSupervisor in the coordinator.
